1. Ce qui était demandé : le cahier des charges YODA

La documentation source du programme (support « Projet YODA — refonte de l'architecture vers GCP ») décrit une transformation en profondeur : quitter une plateforme historique en silos (SQL Server sur MyCloud, datamarts dupliqués, outils fortement couplés comme MicroStrategy, Altair, Talend) pour reconstruire, cas d'usage par cas d'usage, une plateforme GCP organisée en couches et en domaines métier, où les données deviennent des produits partagés, gouvernés, testés et documentés.

1.1 L'architecture cible en 7 couches

CoucheRôleExemple
1. SourcesApplications qui produisent la donnéeImpulse, TecCare, Genesys, Adobe, partenaires, Open Data
2. IngestionPorte d'entrée standardisée avec contrôlesIngestions LUCI (BPCE-SI), fichiers (BPCE-IT)
3. Modèle applicatifDonnées conservées par source, proches de l'origineapp_impulse.raw_contracts
4. Pipeline Factory & ComposerComposants réutilisables + orchestrationtemplates, contrôles, reprises, logs

7. Modèles d'usageAdaptés au consommateurvues BI, features Data Science, API

1.2 Les exigences transverses du support

  • Pipelines robustes : idempotents, observables, rejouables, découplés, testables, paramétrables, sécurisés, documentés (§11.1)
  • Qualité : dimensions (complétude, unicité, validité, cohérence, fraîcheur…) et sévérités pilotant la publication (§12)
  • Rejets : jamais une ligne perdue — donnée d'origine + motif + statut de reprise (§11.3)
  • Conformité by design : classification, moindre privilège, pseudonymisation, durées de conservation (§13)
  • Industrialisation : Git, revues, CI/CD, environnements DEV/PREPROD/PROD, jamais de secret dans le code (§15)
  • FinOps : coûts suivis dès la conception, attribués par domaine et produit (§17)
  • Migration par lots : double run, réconciliation avec le legacy, Go/No Go, décommissionnement (§18)

3. Étape 1 — Le socle logiciel : la Pipeline Factory

Le support YODA parle d'une « Pipeline Factory » : un ensemble de composants standardisés et réutilisables pour construire tous les pipelines. Nous l'avons implémentée comme un package Python (src/yoda/), volontairement sans dépendance au moteur d'exécution : la même logique sert au développement local (fichiers CSV), aux tests automatisés, et sert de spécification exécutable pour le SQL BigQuery.

ModuleResponsabilité (référence au support)
ingestion.pyContrôles de la porte d'entrée (§6.3) : présence, fichier non vide, extension, encodage, colonnes obligatoires, checksum SHA-256, détection de double chargement via un registre des lots (idempotence). Codes d'erreur normalisés ING_001 à ING_006.
transformations/contracts.pyRègles métier du domaine Contrat (§9.4) : harmonisation des statuts, typage, déduplication (dernier événement par contrat), rattachement au référentiel produit, et la règle is_active formalisée et testée sur ses cas limites.
quality.pyFramework de tests qualité (§12) : chaque contrôle porte une dimension et une sévérité. CRITIQUE/ÉLEVÉE bloquent la publication ; MOYENNE publie avec alerte ; FAIBLE alimente le suivi.
rejects.pyGestion des rejets (§11.3) : donnée d'origine + motif + règle en échec + statut de reprise. Aucune ligne écartée silencieusement.
metadata.pyMétadonnées d'exécution (§11.2) : run_id, batch_id déterministe, volumes entrée/sortie/rejets, statut, erreurs. Le batch_id déterministe (source + date + fichier) est la clé de l'idempotence.
pipeline.pyExécution locale de bout en bout (mode démo) : la chaîne complète tourne sans GCP via make demo.
Point d'apprentissage — l'ordre des étapes : le pipeline n'écrit le produit Data qu'après le passage des contrôles bloquants. Si la qualité n'est pas garantie, la publication n'a jamais lieu et les consommateurs restent sur la dernière version saine : mieux vaut des données d'hier que des données fausses.

4. Étape 2 — L'infrastructure as code (Terraform)

Toute l'infrastructure est décrite dans infra/ : rien n'a été créé « à la main » dans la console. C'est le principe Infrastructure as Code : reproductible (dev → preprod → prod avec un simple fichier de variables), relisible en revue de code, et auditable.

4.1 Les ressources provisionnées

  • 18 datasets BigQuery respectant la convention de nommage du support (§10.3) : app_<source> ×7, enterprise_<domaine> ×6, product_<domaine> ×2, usage_<type> ×3, plus ops.
  • Tables d'exploitation : ops.rejects et ops.pipeline_runs, partitionnées par jour ; table produit active_contracts_daily partitionnée par snapshot_date et clusterisée (product_code, channel_code) pour réduire les octets analysés (FinOps §17.2).
  • Buckets GCS : -landing (arrivée des fichiers, purge à 30 jours — un fichier non traité est un incident, pas une archive), -archive (passage en Coldline à 90 jours, suppression à 10 ans à confirmer avec le DPO), -tfstate (état Terraform).
  • IAM moindre privilège : compte de service yoda-pipeline-dev limité à ses buckets et datasets ; groupes BI limités à usage_bi ; labels FinOps (program, comptoir, layer, domain, environment) sur chaque ressource pour l'attribution des coûts.
  • Requête programmée d'orchestration quotidienne (voir étape 7).
# Un dataset par couche et par domaine — extrait de infra/datasets.tf
locals {
  datasets = {
    app_impulse        = { layer = "applicatif", domain = "contrat", ... }
    enterprise_claim   = { layer = "entreprise", domain = "sinistre", ... }
    product_contract   = { layer = "produit",    domain = "contrat", ... }
    usage_datascience  = { layer = "usage",      domain = "transverse", ... }
    ops                = { layer = "transverse", domain = "transverse", ... }
  }
}

5. Étape 3 — Le déploiement réel sur GCP (et ses obstacles)

Cette étape est riche d'enseignements : voici les problèmes réels rencontrés, dans l'ordre, et comment ils ont été résolus. C'est le quotidien d'un Data Engineer.

#Obstacle rencontréCauseRésolution
1gsutil : Permission denied sur PC Windowsgsutil défaillant sous Git Bash (fichiers dans Program Files)Exécuter dans Cloud Shell ; remplacer gsutil par gcloud storage (plus portable)
2billing account… disabled in state absentLe projet n'était lié à aucun compte de facturationLier le compte : gcloud billing projects link
3Cloud billing quota exceededQuota de projets liés au compte de facturation atteint (5)Détacher un projet inutilisé (gcloud billing projects unlink)
4Terraform absent de Cloud ShellGoogle ne préinstalle plus Terraform (un « shim » affiche des instructions)Le script d'installation télécharge Terraform 1.9.8 dans ~/bin automatiquement
5connection refused vers l'API BigQuery, aléatoireInstabilité réseau ponctuelle de Cloud ShellBoucle de retry (3 tentatives, 15 s) autour de terraform apply — sans risque car Terraform est idempotent
Leçon à retenir : en environnement cloud, les échecs transitoires sont normaux. Un bon déploiement n'est pas un déploiement qui ne rate jamais : c'est un déploiement idempotent et retentable, qui reprend là où il s'est arrêté sans jamais dupliquer.

5.1 Les deux scripts de déploiement

  • scripts/deploy_gcp.sh — l'infrastructure : vérification/installation de Terraform, activation des APIs, bucket d'état, terraform apply avec retries, contrôles post-déploiement.
  • scripts/seed_bigquery.sh — les données : chargement des référentiels et des 7 sources brutes, exécution des 3 chaînes de transformation, dépôt des fichiers dans le landing, tableau final des volumes par couche.

7. Étape 5 — Les transformations : de la donnée brute au produit Data

Trois chaînes complètes matérialisent le chemin décrit au §9 du support. Exemple du domaine Contrat :

app_impulse.raw_contracts            (brut, tel que reçu + batch_id)
   │  nettoyage technique : typage, statuts harmonisés, lignes invalides → ops.rejects
   ▼
app_impulse.stg_contracts_clean      (staging)
   │  jointure référentiel produits + déduplication (dernier événement par contrat)
   ▼
enterprise_contract.contracts        (objet métier stable, découplé d'Impulse)
   │  règle d'activité + pseudonymisation SHA-256 du client + photographie du jour
   ▼
product_contract.active_contracts_daily   (partition par snapshot_date)
   │
   ├─→ usage_bi.vw_active_contracts             (KPI agrégés pour Power BI)
   ├─→ usage_datascience.vw_contract_features   (ancienneté, features ML)
   └─→ usage_app.vw_contract_status             (statut à date pour API)

La chaîne Sinistres démontre en plus le croisement de domaines : chaque sinistre est validé contre le domaine Contrat (un sinistre sur contrat inconnu part en rejet ENT_002_UNKNOWN_CONTRACT) et enrichi du produit et du canal de son contrat. La chaîne Interactions démontre l'unification multi-sources : un appel Genesys et un parcours web Adobe deviennent le même objet métier « interaction », comparable et agrégeable.

8. Étape 6 — Qualité, rejets et observabilité

8.2 Le circuit d'un rejet

Une ligne invalide n'est jamais supprimée : elle est stockée dans ops.rejects avec la donnée originale (JSON), le code de règle (ex. STG_004_DATE_ORDER), le message, le lot et un statut de reprise. Le runbook (docs/runbook_contrats_actifs.md) associe chaque code à son diagnostic et à sa correction. Le seuil de rejet est surveillé : au-delà de 5 % (30 % en dev sur le jeu synthétique), la publication est bloquée.

8.3 Le journal d'exécution

Chaque run écrit dans ops.pipeline_runs : run_id, batch_id, date métier, volumes entrée/sortie/rejets, horodatages, statut (SUCCESS / PARTIAL / FAILED), code d'erreur. C'est la base de la supervision (§16) : une chute de volume ou une dérive du taux de rejet se voit en une requête.

9. Étape 7 — L'orchestration : requête programmée et Composer

9.1 Ce qui tourne aujourd'hui : la requête programmée BigQuery (0 €)

La requête programmée yoda-daily-full-chain-dev (provisionnée par infra/scheduler.tf) exécute chaque jour à 05h00 UTC le script sql/orchestration/daily_full_chain.sql : les trois chaînes dans l'ordre des dépendances, une nouvelle photographie quotidienne des produits, et une ligne de journal. Elle tourne avec le compte de service pipeline (et non un compte personnel), grâce à une délégation IAM (serviceAccountTokenCreator accordé à l'agent du Data Transfer Service).

9.2 La cible industrielle : le DAG Composer/Airflow

Le DAG dags/contracts_active_daily.py est prêt pour Composer et apporte ce que la requête programmée ne sait pas faire :

  • Capteur de fichier : attend l'arrivée du fichier Impulse dans le landing (vérification toutes les 5 min, timeout 2 h puis alerte) ;
  • Contrôles d'ingestion avant chargement ; chargement raw en WRITE_TRUNCATE sur la partition du jour ;
  • Tests qualité bloquants en parallèle (BigQueryCheckOperator) entre le produit et la publication ;
  • Reprise fine : relancer une seule tâche, ou rejouer une date passée (backfill) grâce au templating {{ ds }} ;
  • Archivage du fichier source après traitement.
Décision coût : Cloud Composer facture ~300-400 €/mois même à l'arrêt. Il a été volontairement exclu du déploiement : la requête programmée couvre le besoin quotidien du bac à sable, le DAG restant prêt pour l'environnement d'entreprise (où Composer est fourni par la plateforme Groupe).

9.3 Requête programmée vs Composer — le comparatif

10. Sécurité, RGPD et FinOps

  • Moindre privilège : le compte de service pipeline n'a que les droits nécessaires ; les consommateurs BI ne voient que usage_bi, jamais les couches internes (protection des structures, §6.7).
  • Pseudonymisation : customer_id est haché (SHA-256 salé) dès la couche produit — les usages BI et Data Science n'ont pas besoin de l'identité (minimisation RGPD §13.3).
  • Aucun secret dans le code : configuration non sensible dans config/<env>.yaml ; secrets via Secret Manager et comptes de service.
  • Classification : chaque source est classée dans son contrat de données (personnelle, publique…).
  • Cycle de conservation : landing purgé à 30 jours, archive en Coldline à 90 jours, suppression à échéance (durées exactes à valider avec le DPO).
  • FinOps : partitionnement + clustering (moins d'octets analysés), labels d'attribution des coûts par domaine/couche/environnement, vues d'agrégats pour les usages fréquents, et recommandation d'une alerte de budget (5 €) sur le projet.

11. Industrialisation : Git, tests et CI/CD

  • Dépôt structuré selon le §15.3 du support : dags/ src/ tests/ config/ schemas/ docs/ infra/ requirements/ pipeline.yml.
  • 36 tests automatisés (unitaires + intégration) : contrôles d'ingestion, règles métier avec cas limites, framework qualité, chaîne complète de bout en bout, idempotence des relances, échec propre sur fichier manquant.
  • CI GitHub Actions (.github/workflows/ci.yml) : lint (ruff) + tests (pytest) + exécution de la démo + validation Terraform à chaque Pull Request.
  • Cloud Build (cloudbuild.yaml) : chaîne de déploiement continu depuis GitHub (tests → Terraform → données de référence → sync DAGs optionnelle).
  • Chaîne de promotion décrite dans pipeline.yml : DEV automatique, PREPROD et PROD sur validation manuelle (recette, double run, Go/No Go §18.4), avec stratégie de rollback.
